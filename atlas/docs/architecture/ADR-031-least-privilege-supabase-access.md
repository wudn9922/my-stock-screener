# ADR-031 — Supabase 最小權限存取（Least privilege）

狀態：Proposed（2026-11-27）。本 ADR 只提出設計與遷移順序；不部署、不變更程式、SQL、RLS、排程、IAM 或密鑰。每階段另開任務，經維護者驗收後才切換。

## 1. 背景、範圍與證據

`SUPABASE_SERVICE_ROLE_KEY` 使請求以具 BYPASSRLS 的 service_role 身分存取 Data API；實際可及範圍還取決於 schema exposure、GRANT 及 RPC，不代表任意 PostgreSQL 超級使用者權限。現有 LINE 身分、owner filter、cloud grant、RLS 與 mutation trigger 是正常程式路徑的防護，不足以限制被偷走的 service-role 憑證。攻擊者可繞開 Python/TS 的篩選，直接呼叫已授權的 Data API/RPC，包括持股、成交及 MEXC 連線等。私有 schema 不直接暴露並不等於其 SECURITY DEFINER RPC 安全；MEXC 加密憑證也不等於明文可直接由資料庫金鑰解密，但仍有資料外洩與篡改風險。

盤點基準：main `3e649600d297c7c063bf6538be606fbb6b1eac8d`。因無法 clone，使用 GitHub 全 repo 索引搜尋（`SUPABASE_SERVICE_ROLE_KEY`、`SUPABASE_SERVICE_ROLE`、`service_role`、`SUPABASE_SECRET_KEY`、`sinopac-supabase`、`get_supabase_key`、`SupabaseStore(`、`screener-symbols.mjs`、`refresh:watchlists`、`X-Sinopac-Secret`、`X-Statement-Secret`、JWT 相關詞），逐一讀取原檔、以行級匹配及呼叫鏈交叉核對。這是 grep 的替代方式，不聲稱執行過本地 git grep 或完整非索引檔案掃描。後續實作前在 checkout 複核（只列檔名或遮罩內容，不印憑證）：

```sh
git grep -ilE 'SUPABASE_SERVICE_ROLE(_KEY)?|SUPABASE_SECRET_KEYS?|service_role|sinopac-supabase|get_supabase_(service_)?key|SupabaseStore\(|screener-symbols\.mjs|refresh:watchlists'
git grep -ilE 'jwt_secret|signing_keys|X-Sinopac-Secret|X-Statement-Secret'
```

以下所有路徑均從 repo 根目錄起算，行號對應上述基準；SQL 是 repo 定義，不宣稱每一個手動 SQL 已部署。已辨識 **11 個邏輯執行面**：2 個 Actions 工作步驟、4 個 Cloud Run runtime、4 個 Edge Functions、1 個可獨立執行的腳本（未確認有現役排程）；部署 workflow/共用函式另列，不重複計數。測試、範例、文件及 GRANT 本身不是金鑰持有的 runtime。實際 Cloud Run env/Secret Manager 綁定版本、Actions secrets 值、外部 Render 是否仍運作、DB 實際 grants 皆須維護者複核；未讀取任何憑證內容或個人資料列。

## 3. 方案與 signing-key 查證

### A. 自訂 Postgres role + 最小權限 JWT

- 可行條件：建立 NOLOGIN、NOBYPASSRLS、非 owner 的分服務 role；僅授予 authenticator SET ROLE 所需 membership、schema USAGE、列級 RLS 及必要 column SELECT/UPDATE/EXECUTE。不能授予 role service_role、postgres 或可 SET ROLE 成高權限身份；查 inherited/PUBLIC/default grants、sequence、exposed schema 與 SECURITY DEFINER。由固定 server-side issuer 簽短效 JWT（role、exp、必要可信 owner/account claims）；Data API 使用 publishable/anon 作 apikey，JWT 作 Authorization。LINE user ID 為 text，不是 auth.uid() 的 UUID；應以可信簽章的 claim 或服務端映射與 DB policy 驗證，不能信任 caller body、user_metadata。若固定 owner，最好由 DB 映射或 restricted RPC 決定。
- legacy JWT secret 可簽任意 role，包括 service_role，**絕不可把 signing secret 給 Actions/Cloud Run**。新 managed signing keys 的私鑰不能匯出；官方支援自行產生並匯入 signing key、啟用後由持有私鑰的 issuer 簽 JWT，role 必須對應現有 DB role。自訂 role 能否經此專案 gateway/PostgREST 驗證及 impersonate，需在 staging 驗證 membership 與實際 JWT，不能只驗 JWT 字串。短效 token 並非立即可撤銷；停發、撤 grant 或 issuer identity 可降低窗口。
- **本專案 signing mode：需維護者在 Dashboard 確認。** 已用唯讀 Supabase project metadata（list/get project）確認 my-stock-screener 專案存在，回傳沒有 signing mode。supabase/config.toml:165-169 的 signing_keys_path 只是註解，並非 hosted 設定；supabase_store.py:298-303、webPush.ts:291-314 兼容 legacy JWT 與新版 secret 格式，也不能推知現行 signing system。未索取/解碼實際 API key、未讀私鑰、未執行 SQL。維護者檢查 Dashboard 的 JWT Keys（current/standby/previous/revoked、legacy shared secret 或 signing keys、是否 imported）、API Keys（legacy 是否啟用、新 key）、Data API exposed schemas。記錄類型與狀態，不複製任何值。公有 JWKS 只能說明公開驗證 keys，不能單獨證明 legacy 已禁用。
- 效果：偷到 scoped JWT 只能操作該 role/row/column/RPC，不能跨域帳務；issuer 私鑰被偷仍可能冒充高權限角色。RLS 不限制 SECURITY DEFINER owner，仍需明確 scope 的 RPC、fixed search_path、REVOKE EXECUTE FROM PUBLIC/anon/authenticated，prefer SECURITY INVOKER；不得讓 restricted role 直接執行可任選 owner 或任意 operation 的舊 generic RPC。
- 成本：中高（SQL roles、grants、RLS、token issuer、refresh/rotate、驗證、claim schema）；需改 Supabase DB，若匯入新 signing key 亦需改 Auth 設定與測試 session 相容。既有 client 需改 header/refresh，持股/推播 RPC 等須縮小。優點是 DB 原生強制；不作第一階段，因 signing mode 未確認且不應為報表先引入高權限 signer。

### B. 專用 Edge Function + 每服務獨立共享密鑰（建議先採用）

- 每個 caller 一把不同的高熵隨機密鑰（report、watchlist、monitor、push、discord、sinopac、statement 分開；名稱只是提議，不是現存值）；caller 只有該 key，不持任何 service role/secret key 或 signer。以 TLS + 固定專案 URL、專用 header（例如 X-Atlas-Job-Secret，禁止任意 redirect、限制請求大小/方法、常數時間比對 digest）、owner/account 綁定於服務端設定；必要時 timestamp/nonce 或 request ID、限流和 idempotency。不得接受任意表名、任意 RPC、自由 select/filter、caller 自選 owner；服務端只做 allowlisted actions 與驗證過的 payload，輸出欄位最小化，no-store、禁止敏感 log。
- 可參考現有兩種方向：user-settings/sinopac.ts:77-94 → sinopac_sync/app.py:62-120 的 X-Sinopac-Secret + IAM；statement_sync/app.py:52-54、statement_sync/README.md:15-21 與 apps_script/Code.gs 的 X-Statement-Secret。這些是現有入站驗證，**不可重用同一密鑰作反向 DB 授權**。目前 push.notify 用 server key 且探測 RPC；另設獨立 push header/endpoint，移除 probe，固定 owner、限 title/body/url/tag，保留 consent/去重。
- 函式可先用現行 server-side DB client（集中信任邊界，禁止把 key 轉回 caller），對 report 只回傳群組/股票/指數必要欄位；watchlist 只更新 observation 子欄位（server merge、CAS，不能改 filter/owner）；broker adapter 僅固定帳戶的狀態、revision/持股替換或 statement ingest/applied 操作，避免完整 owner document。
- 效果：runner/Cloud Run 套件遭植入，偷到其 key 也只能使用白名單能力；仍可能外洩該功能必要資料、發送偽告警、寫壞該帳戶，須 DB 約束、rate limits 與稽核。Edge compromise 仍高權限（平台注入 server keys/DB URL；分函式本身不提供真正 secret 隔離）。因此 B 是第一道隔離，長期以 A 或 C 在 DB/不同 trust domain 強化。不能以「每服務一個 sb_secret_ key」冒充最小權限：它們可獨立輪替，但仍映射 service_role/BYPASSRLS。
- 成本：中（新增少量 Deno handler、單元測試、deploy + 每服務 secrets、密鑰輪替；無須一開始動 hosted JWT key、RLS 或直接授權新角色）。需在 Supabase 設定新增 secrets/部署 endpoint，對自訂 header 的新 endpoint 才設 verify_jwt=false 並在每條路徑先驗證；使用 publishable apikey 若 gateway 需要，不當作身分驗證。不要改現有 LINE endpoint 的 JWT 設定或匿名 RLS。保留舊呼叫合約直到新服務驗收，新增功能可回滾。

### C. 專用 Postgres login / RPC-only DB gateway（較強的長期隔離）

- 各服務只持一個非 superuser、NOBYPASSRLS、非 table owner、無高權限 membership 的 LOGIN role（直連 TLS 或 Supavisor 依官方支援模式；驗證 IPv4/IPv6、pooler mode、connection limits）；只允許執行針對該功能的 restricted RPC，或 narrowly granted view/columns+RLS。獨立極小 gateway（或受控 Cloud Run，使用 IAM/OIDC，而非可由所有 Edge runtime 讀取的 default key）持有有限 DB credential；不要給 gateway Postgres 管理員密碼。驗證 IAM audience/subject，service-to-service 身分綁定；Gmail Apps Script 保留既有共享 secret 入站、由 statement runtime 呼叫 gateway。避免把 DB password 放入大型行情/PDF/SDK 程序，若直接放也必須是 scoped role。
- 可採 SECURITY INVOKER；若必要 SECURITY DEFINER，使用最小權限 owner、固定 search_path 與 schema-qualified SQL、明確操作/owner/account/payload、事務及 RLS/trigger；撤回 PUBLIC EXECUTE 並限制新 roles 的有效 grants。不能依 client filter 或傳入 line_user_id 當唯一防護。
- 效果：憑證外洩不依賴應用路由即受 DB 強制，無需自簽 JWT；獨立 gateway 不含 Edge 自動注入高權限 secrets，降低 broker/行情彼此污染。缺點：DB credential/網路/Pg driver、pooling、交易、secret rotation/服務營運額外成本；直連 DB 與 Data API 行為不同，須驗 CAS、trigger、timeout、idempotency。需改 DB grants/RLS/RPC 和 Secret Manager/IAM，可能增加少量費用與延遲；先 staging 測，非本 PR。

### D. 只拆 runner / 靜態投影（輔助，不單獨足夠）

把 report/watchlist 資料取得放乾淨、只具 B 或 C credential 的短生命 job；只傳最小輸入/結果，金融資料不得進 GitHub artifacts、cache、Pages、stdout，private watchlist 用受控暫存（更佳：在 gateway 內運算/驗證）。report 只發布已授權公開投影，保存原 owner policy 與撤權語意。純公開市場採集、build、第三方套件安裝 job 不應含任何 DB secret；runner 隔離、actions pin SHA、依賴 lock/hash/SBOM、縮小 runtime requirements、掃描及 egress allowlist 為補強。若乾淨 job 仍持 service-role，攻擊其本身仍能全域存取；不算完成。成本低至中，需 workflow 拆分及維護 private transfer 安全，不必改 RLS/JWT；先用 B 避免發布或 schedule 中斷。

官方依據（查閱 2026-11-27）：[API keys](https://supabase.com/docs/guides/getting-started/api-keys)、[JWT signing keys](https://supabase.com/docs/guides/auth/signing-keys)、[JWT](https://supabase.com/docs/guides/auth/jwts)、[Edge secrets](https://supabase.com/docs/guides/functions/secrets)、[Edge auth headers](https://supabase.com/docs/guides/functions/auth-headers)、[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Data API security](https://supabase.com/docs/guides/api/securing-your-api)、[PostgREST JWT roles](https://docs.postgrest.org/en/stable/references/auth.html)。Legacy key 退役時程以當期官方公告/Dashboard 為準，不假設現在已停用。

### 4.1 通用驗收與不可退讓的限制

1. 遷移先部署兼容新入口，再切換呼叫端；所有正式 mutation 只允許單一 writer（不雙寫/不重複通知）；保持 scheduler、LINE/Discord/Web Push、holdings sync 正常。切換前記錄 revision、lease、去重鍵與最後成功時間；無法驗證就不切，不以故意停排程換取安全。
2. 正向/負向測試對每把 scoped credential：合法功能、缺/錯/過期 key、交叉服務 key、任意 owner/account、未授權 table/RPC（包括 holdings/MEXC/statement/admin policy/push）、無 cloud grant 或撤權途中；測試無法列出密鑰/帳務回應。A/C 額外以實際 role 測 effective grants、RLS USING/WITH CHECK、PUBLIC EXECUTE、SECURITY DEFINER search_path、不可升權；不能只驗 HTTP 200 或「UI 看不到」。在測試環境使用合成資料，production 只做維護者明確授權的正常業務驗收、計數/狀態核對。
3. 部署時保留版本化舊路徑短暫回滾（限原 runtime，明確到期），新憑證獨立輪替（先驗收新、再移除舊，server 短期雙 key）；不得把 secret 放 Git、artifact、cache、Pages、log、截圖、可讀 CLI history 或測試 fixture。任何錯誤都不能 fallback 到 anon 全表讀取或重新開 RLS。新增 SQL/Edge 及權限變更另開 PR，先在 staging 查 advisor/negative tests。
4. 可觀測性只記 route/service identity 的非敏感標籤、HTTP/SQL error code、耗時、aggregate counts、revision/conflict、delivery/sync 成功時間、request ID；不記 headers/body、使用者 ID、持股、成交、PDF、密鑰。若發現異常存取，依 incident plan 即時限制受影響 credential、查 audit 並另行處理，不等待本 ADR 全部階段。
5. Deno hosted 預設 secrets 的暴露面不能靠刪除程式 env read 解決；以 scoped DB role 或獨立 trust domain 實現真正限制。此 ADR 的第一里程碑是高風險 **外部執行環境不再取得 service role**；最終里程碑是跨資料域最小權限與不可升權的實測。

## 5. 本 ADR 的驗證

僅文件：原始碼逐檔行級查證、call chain、SQL 定義、依賴清單、官方文件與 project metadata；無 clone／本地完整 lint/build/test，不能聲稱已跑本地 git status。以 PR remote compare 確認唯一變更是本 Markdown，並讀取最新提交所有適用 CI 結果。無實際部署、SQL query、密鑰內容讀取、權限或排程變更；未驗證 production 真實 grants/runtime secrets/signing mode。未來各階段的測試與手動操作均是計畫而非完成事項。
